**Overall Assessment:** The application is well-structured and follows good practices for a WinForms system tray utility. No critical vulnerabilities were found. The most actionable issues are a dictionary race condition on `_lastAlertTimes`, GDI handle leaks from `GetHicon()`, and non-atomic config file writes. The v1.11.0 system-wide RAM alert feature amplifies the existing threading issues (more timer-thread dictionary access) and adds a new font leak.

## 1. Security Issues

### SEC-01: Named Mutex Squatting (Low)
**File:** `Program.cs:10`
**Description:** The single-instance mutex `Global\RamWatchdog_SingleInstance` uses a predictable name. A malicious process could create this mutex first, preventing RAM Watchdog from starting (denial-of-service on the app itself).
**Impact:** An attacker with local execution can block the app from launching.
**Recommendation:** Low priority since this requires local execution already. If desired, detect this by checking whether the existing mutex owner is actually a RamWatchdog process, or use a less predictable name.

### SEC-02: Config File Tampering — No Input Validation on Deserialized Values (Medium)
**File:** `Config.cs:37-51`
**Description:** `Config.Load()` deserializes `%APPDATA%\RamWatchdog\config.json` via `System.Text.Json` without validating the ranges of deserialized numeric fields. A tampered config file could set `ThresholdGB` to negative values, extremely large values, or `NaN`/`Infinity`. The new `SystemUsageThresholdPercent` (int) is also unvalidated — values outside 0-99 could cause the system alert to fire constantly or never.
**Impact:** Could cause division-by-zero, nonsensical threshold behavior, or unexpected rendering. Not exploitable for RCE, but could degrade application behavior.
**Recommendation:** Add range validation in `Config.Load()` (or a post-load validation method) to clamp/reject out-of-range values:
```csharp
// After deserialization:
if (config.ThresholdGB < 0 || config.ThresholdGB > 128) config.ThresholdGB = 0;
if (config.ThresholdPercent < 0 || config.ThresholdPercent > 90) config.ThresholdPercent = 0;
if (config.DisplayFloorGB < 0 || config.DisplayFloorGB > 64) config.DisplayFloorGB = 0;
if (config.SystemUsageThresholdPercent < 0 || config.SystemUsageThresholdPercent > 99)
    config.SystemUsageThresholdPercent = 90;
```

### SEC-03: Non-Atomic Config File Writes (Medium)
**File:** `Config.cs:53-58`
**Description:** `File.WriteAllText(ConfigPath, json)` writes directly to the config file. If the process crashes or is killed mid-write, the file could be left in a corrupt/truncated state.
**Impact:** Config corruption on next load (mitigated by the try/catch fallback to default config, but user settings are lost silently).
**Recommendation:** Use write-to-temp-then-rename pattern:
```csharp
string tempPath = ConfigPath + ".tmp";
File.WriteAllText(tempPath, json);
File.Move(tempPath, ConfigPath, overwrite: true);
```

### SEC-04: Registry Auto-Start Path Injection (Low)
**File:** `MainForm.cs:639-640`
**Description:** The auto-start registry entry stores the executable path quoted: `$"\"{exePath}\""`. This is correct and prevents argument injection via spaces in the path.
**Status:** Properly handled. The quoting prevents execution of unintended arguments. No issue.

### SEC-05: Hardcoded URL with `UseShellExecute` (Low)
**File:** `Dialogs.cs:260`
**Description:** `Process.Start()` with `UseShellExecute = true` opens the GitHub releases URL. Since the URL is a compile-time constant (not user-supplied), there is no URL injection risk.
**Status:** Safe as implemented.

### SEC-06: Process Enumeration Information Disclosure (Info)
**File:** `MemoryMonitor.cs:103-147`, `MainForm.cs:527-612`
**Description:** The app reads process names and memory usage of ALL running processes and can export them to a markdown file. The saved report in `Documents\RamWatchDog\` contains a full process list snapshot.
**Impact:** If report files are accessed by another user/process on a shared machine, this reveals what software is running and its memory footprint.
**Recommendation:** Informational only. Reports are saved to the user's own Documents folder with appropriate default permissions.

### SEC-07: Silent Exception Swallowing Hides Security-Relevant Failures (Info)
**File:** `Config.cs:50`, `MemoryMonitor.cs:92-96`, `MainForm.cs:238`
**Description:** Multiple catch blocks swallow all exceptions without logging. If a security-relevant failure occurs (e.g., file permission denied, corrupted config), it is silently ignored.
**Recommendation:** Consider adding minimal logging (e.g., to `Debug.WriteLine`) for swallowed exceptions to aid troubleshooting.

## 2. Resource Leaks

### LEAK-01: GDI Handle Leak from `GetHicon()` — HICON Never Destroyed (High)
**Files:** `MainForm.cs:366-367`, `AlertIcon.cs:21-22`
**Description:** Both `LoadAppIcon()` and `CreateAlertIcon()` call `bmp.GetHicon()` which allocates a native HICON handle. `Icon.FromHandle()` wraps the HICON but does **not** take ownership of it. The subsequent `.Clone()` creates a new managed icon (good), but the original HICON from `GetHicon()` is never freed via `DestroyIcon()`.

```csharp
// Current (leaks HICON):
var icon = Icon.FromHandle(bmp.GetHicon());
return (Icon)icon.Clone();

// Fixed:
IntPtr hIcon = bmp.GetHicon();
try
{
    using var tempIcon = Icon.FromHandle(hIcon);
    return (Icon)tempIcon.Clone();
}
finally
{
    DestroyIcon(hIcon); // P/Invoke to user32.dll
}
```

**Impact:** Two GDI handles leaked at startup (one per icon). Since these are called once at startup and cached, the leak is bounded. However, it violates best practices and would be worse if icons were regenerated frequently.
**Severity:** High for correctness; low practical impact due to one-time call.

### LEAK-02: Font Leaks in Settings Dialog (Medium)
**File:** `Dialogs.cs:183`, `Dialogs.cs:218`
**Description:** Two `new Font("Segoe UI", 8f)` instances are created — one for the display floor hint label (line 183) and one for the system usage hint label (line 218, added in v1.11.0). When the dialog is disposed, WinForms does **not** automatically dispose fonts assigned to controls. This leaks two `Font` GDI objects each time the Settings dialog is opened.
**Recommendation:** Define a single static cached `Font` for 8pt hint text (like the other fonts in MainForm) and reuse it for both labels:
```csharp
private static readonly Font FontHint = new("Segoe UI", 8f);
```

### LEAK-03: Font Leak in Help Dialog (Medium)
**File:** `Dialogs.cs:388`
**Description:** `new Font("Segoe UI", 9.5f)` is created for the RichTextBox in the Help dialog. Same issue as LEAK-02 — the font is leaked when the dialog closes.
**Recommendation:** Cache as a static field or dispose on dialog close.

### LEAK-04: Potential Double-Dispose in ExitApp / Dispose (Low)
**File:** `MainForm.cs:683-695`
**Description:** `ExitApp()` disposes `_monitor` and `_trayIcon`, then `Application.Exit()` triggers `Dispose(bool)` which disposes them again. While `MemoryMonitor.Dispose()` has a `_disposed` guard, the `_trayIcon.Visible = false` call in `Dispose(bool)` could throw `ObjectDisposedException` if `_trayIcon` was already disposed in `ExitApp()`.
**Recommendation:** Add a disposed guard:
```csharp
protected override void Dispose(bool disposing)
{
    if (disposing)
    {
        _monitor.Dispose();
        if (!_trayIcon.IsDisposed)
        {
            _trayIcon.Visible = false;
            _trayIcon.Dispose();
        }
        _trayMenu.Dispose();
    }
    base.Dispose(disposing);
}
```

### LEAK-05: Static GDI Objects Never Disposed (Low)
**File:** `MainForm.cs:27-37`
**Description:** Static fonts (`FontNormal`, `FontSmall`, etc.), brushes (`BrushBgPanel`, `BrushFgBright`), pens (`PenBorder`), and StringFormats (`FmtLeft`, `FmtRight`) are allocated once and never disposed.
**Status:** This is **intentional and acceptable** — these are process-lifetime singletons used in drawing hot paths. Disposing them would cause crashes in owner-draw callbacks. The OS reclaims all handles on process exit. No action needed.

## 3. Threading & Race Conditions

### RACE-01: `_lastAlertTimes` Dictionary Race Condition (High)
**File:** `MainForm.cs:83, 394-404, 408-428, 510, 521`
**Description:** The `_lastAlertTimes` dictionary is accessed from **two different threads** without synchronization:
- **Timer thread** (via `OnMonitorSnapshot` → `CheckAlerts`): reads and writes entries at lines 400-402
- **Timer thread** (via `OnMonitorSnapshot` → `CheckSystemUsageAlert`): reads and writes entries at lines 416-418 *(new in v1.11.0)*
- **UI thread** (via `OnIgnoreSelected`): calls `_lastAlertTimes.Remove()` at line 510
- **UI thread** (via `OnSettings`): calls `_lastAlertTimes.Clear()` at line 521

The v1.11.0 system-wide alert feature adds a second timer-thread access path (`CheckSystemUsageAlert`), increasing the frequency of cross-thread dictionary operations.

`Dictionary<TKey, TValue>` is **not thread-safe**. Concurrent read/write can cause corrupted internal state, infinite loops in bucket chains, or `NullReferenceException`.
**Recommendation:** Either:
1. Use `ConcurrentDictionary<string, DateTime>` instead
2. Move `CheckAlerts` and `CheckSystemUsageAlert` inside the `BeginInvoke` callback so all dictionary access happens on the UI thread
3. Add a `lock` around all dictionary access

Option 2 is simplest and keeps everything on the UI thread:
```csharp
private void OnMonitorSnapshot(List<ProcessMemoryInfo> snapshot)
{
    _latestSnapshot = snapshot;
    if (!IsDisposed && IsHandleCreated)
    {
        try
        {
            BeginInvoke(() =>
            {
                if (_config.NotificationsEnabled && !_config.AlertsSilenced)
                {
                    CheckAlerts(snapshot);
                    CheckSystemUsageAlert();
                }
                _trayIcon.Text = tooltip;
                UpdateListView(snapshot);
            });
        }
        catch (ObjectDisposedException) { }
    }
}
```

### RACE-02: Non-Volatile Long Field Access Across Threads (Medium)
**File:** `MemoryMonitor.cs:33-34, 70-78, 138-140`
**Description:** `_thresholdBytes` and `_displayFloorBytes` are `long` fields written from the UI thread (`SetThreshold`, `SetDisplayFloor`) and read from the timer thread (`BuildSnapshot`). While `long` reads/writes are atomic on x64, the C# memory model does not guarantee visibility across threads without `volatile` or explicit barriers. The timer thread may read stale cached values.
**Impact:** After changing settings, the new threshold may take an extra poll cycle to take effect. Low practical impact.
**Recommendation:** Use `Volatile.Read`/`Volatile.Write` or `Interlocked.Exchange`/`Interlocked.Read`:
```csharp
public void SetThreshold(long bytes) => Interlocked.Exchange(ref _thresholdBytes, bytes);
// In BuildSnapshot:
long threshold = Interlocked.Read(ref _thresholdBytes);
```

### RACE-03: `_currentMemoryLoadPercent` Cross-Thread Access (Medium)
**File:** `MemoryMonitor.cs:35, 84, 108`
**Description:** The `_currentMemoryLoadPercent` field (uint, added in v1.11.0) is written by the timer thread in `BuildSnapshot()` (line 108) and read from the UI thread via `CurrentMemoryLoadPercent` property in `UpdateListView()` (MainForm.cs:485) and `CheckSystemUsageAlert()` (MainForm.cs:412). While `uint` reads/writes are atomic on all .NET platforms, there is no memory barrier guaranteeing cross-thread visibility.
**Impact:** Low — the UI could see a one-cycle-stale percentage value. System alerts may fire one poll cycle late.
**Recommendation:** Use `Volatile.Read`/`Volatile.Write` for correctness:
```csharp
// Write:
Volatile.Write(ref _currentMemoryLoadPercent, memStatus.dwMemoryLoad);
// Read:
public uint CurrentMemoryLoadPercent => Volatile.Read(ref _currentMemoryLoadPercent);
```

### RACE-04: `_latestSnapshot` Reference Assignment (Medium)
**File:** `MainForm.cs:85, 374, 529`
**Description:** `_latestSnapshot` is assigned on the timer thread (line 374) and read on the UI thread in `OnSaveReport` (line 529). Reference assignments are atomic on .NET, so there's no torn-read risk. However, without a memory barrier, the UI thread could theoretically read a stale reference.
**Impact:** Minimal — the save report would just capture a slightly older snapshot. Since `BuildSnapshot()` creates a new list each cycle and never mutates published lists, there is no data corruption risk.
**Recommendation:** Mark as `volatile` for correctness:
```csharp
private volatile List<ProcessMemoryInfo> _latestSnapshot = [];
```

## 4. Error Handling

### ERR-01: Silent Config Corruption Recovery (Medium)
**File:** `Config.cs:42-54`
**Description:** If `config.json` is corrupted (truncated write, invalid JSON, etc.), `Config.Load()` silently returns a default config. The user's settings (ignored processes, threshold, floor) are lost without notification. The next `Save()` call overwrites the corrupted file with defaults.
**Recommendation:** Consider backing up the existing config before overwriting on corruption, or showing a one-time notification that settings were reset.

### ERR-02: No Validation of `Environment.ProcessPath` (Low)
**File:** `MainForm.cs:351, 639`
**Description:** `Environment.ProcessPath` can return `null` in some edge cases (e.g., single-file apps on certain runtimes). The code falls back to `Application.ExecutablePath` which is acceptable. However, `Path.GetDirectoryName` on the fallback could also return null if the path is a root.
**Impact:** Very edge-case; would cause `Path.Combine` to throw `ArgumentNullException`.
**Recommendation:** Add a null guard:
```csharp
string? exeDir = Path.GetDirectoryName(
    Environment.ProcessPath ?? Application.ExecutablePath);
if (!string.IsNullOrEmpty(exeDir)) { ... }
```

### ERR-03: Timer Callback Can Fire After Dispose (Low)
**File:** `MemoryMonitor.cs:86-97, 180-188`
**Description:** `System.Threading.Timer.Dispose()` does not guarantee that callbacks already queued on the thread pool will not execute. A `Poll` callback could fire after `_disposed` is set to true, potentially calling `OnSnapshot` on a partially-disposed form.
**Impact:** Could cause `ObjectDisposedException` in rare shutdown timing. Mitigated by the catch in `OnMonitorSnapshot`.
**Recommendation:** Check `_disposed` at the top of `Poll`:
```csharp
private void Poll(object? state)
{
    if (_disposed) return;
    // ...
}
```

## 5. Code Quality

### QUAL-01: Hardcoded Version Fallback Is Stale (Medium)
**File:** `MainForm.cs:10`
**Description:** The fallback version string `"1.6.0"` is outdated — the current version is `1.11.0`. If `Assembly.GetName().Version` returns null for any reason, the title bar shows a wrong version.
**Recommendation:** Update fallback to match the current version, or use a compile-time constant derived from the `.csproj` Version property.

### QUAL-02: IgnoredProcesses List — Linear Search (Low)
**File:** `Config.cs:63`
**Description:** `IsIgnored` uses `List.Contains` with a `StringComparer`, which is O(n) per call. This is called for every process in every snapshot (every 2 seconds). With a large ignore list, this could add up.
**Impact:** Negligible with typical ignore lists (< 50 items). Would only matter with hundreds of ignored processes.
**Recommendation:** If needed, replace with a `HashSet<string>(StringComparer.OrdinalIgnoreCase)`.

### QUAL-03: `CheckAlerts` Unbounded Dictionary Growth (Low)
**File:** `MainForm.cs:402`
**Description:** `_lastAlertTimes` entries are added whenever a process exceeds the threshold but never cleaned up for processes that stop running or drop below threshold. Over long uptimes with many transient processes, this dictionary grows without bound.
**Recommendation:** Periodically prune entries older than `AlertCooldown` or entries for processes no longer in the snapshot.

### QUAL-04: `ToastNotification` Screen Positioning Null Safety (Info)
**File:** `ToastNotification.cs:31`
**Description:** `Screen.PrimaryScreen` can return `null` on headless systems or remote sessions. The fallback `Screen.GetBounds(Point.Empty)` is used, which is correct.
**Status:** Properly handled.

## 6. Pipeline / Build Concerns

### BUILD-01: No TreatWarningsAsErrors in csproj
**File:** `RamWatchdog.csproj`
**Description:** The CLAUDE.md states "treat warnings as errors" but the `.csproj` does not include `<TreatWarningsAsErrors>true</TreatWarningsAsErrors>`. Warnings could slip through without breaking the build.
**Recommendation:** Add to the PropertyGroup:
```xml
<TreatWarningsAsErrors>true</TreatWarningsAsErrors>
```

### BUILD-02: No Code Signing
**Description:** The published single-file EXE is not code-signed. Windows SmartScreen may flag it as untrusted when users download it.
**Recommendation:** Consider code signing for public distribution.
